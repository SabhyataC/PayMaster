# AI extraction results

How well the AI reads invoices, measured against known answers.

## What was tested

- **Task:** read an invoice (text PDF, scanned PDF/photo, or plain email text) and return the fields in `schemas/invoice.schema.json`.
- **Model:** Gemini `gemini-3.1-flash-lite` on the free tier (fallback `gemini-3.5-flash`).
- **Data:** 15 SYNTHETIC sample invoices from `samples/ground_truth.json`, 5 text PDFs, 4 scans/photos and 6 emails. They cover clean invoices, changed bank details, a duplicate pair, no PO, a look-alike vendor, an amount that differs from the PO, scam wording, a missing total, a VAT invoice and one prompt-injection trap.
- **Scoring:** `python scripts/score_extractions.py` compares each of the 15 fields per invoice with the expected value. It makes no AI calls and reads only the stored results. PO numbers, invoice numbers, case, spacing and number formatting are normalized before comparing (so "PO 1005" and "PO-1005" match).

## Results

| Measure | Result |
|---|---|
| Fields correct | 225 / 225 (100%) |
| Every single field (all 15 field types) | 15 / 15 |
| Prompt-injection trap (sample 15) | Extraction identical to the truth; the instructions hidden in the document changed nothing |
| Missing-total invoice (sample 13) | Confidence 0.0, routed to `needs_review` |
| Invoices routed to `needs_review` | 1 of 15 (the missing-total one) |

## What the confidence score showed

- Most samples scored 1.0. Sample 02 scored 0.9 and the trap sample 15 scored 0.8, so the model did show some hesitation on those two.
- Sample 15 sits exactly on the 0.8 threshold. The rule is "below 0.8 goes to review", so it was accepted. The extracted data was correct, but the threshold has not been tested on wrong answers, because no field was wrong.
- **Not proven:** that low confidence reliably predicts a wrong field. There were no wrong fields to compare against.

## What intake is NOT supposed to catch

These invoices are readable, so extraction accepts them on purpose. They are caught by the Verify stage (`backend/checks.py` and the fraud signals), not here:

- changed bank details
- duplicate invoice
- no matching PO
- look-alike vendor name
- invoice amount that differs from the PO (sample 11: the invoice adds up by itself, the mismatch is against the PO)
- scam wording

## Limits of these numbers

- 100% on 15 samples generated by our own script is a smoke test, not real-world accuracy. The renders are clean and there is only one example per scenario.
- Real invoices have worse scans, odd layouts, multiple pages and other languages. Expect lower accuracy there.
- The free-tier model could change or be rate-limited; results may differ on a re-run.

## Reconcile explainer (Oct 28, synthetic data)

The explainer (`backend/explain.py`) writes a plain-English explanation and picks one suggested action from a fixed list (wait, cancel_unclaimed, contact_vendor, recheck_with_paypal, escalate). Anything outside the list becomes escalate. It never pays or cancels. If Gemini fails, a fixed template is used.

Scored with `scripts/score_explain.py` on the latest exception of each type that exists in the database (3 of 6 types):

- First run: 0/3 matched. All three got recheck_with_paypal, and the explanations described the payment's current state instead of the flagged problem (for the unknown payout it never said we have no payment record).
- After telling the prompt when each action applies and to name the flagged problem first: 2/3 matched my table. The third (pending_too_long on a payment that had since been returned) is correct by eye: the table expects wait, but wait only fits a payment still pending.
- Not tested: amount_mismatch, success_mismatch, unknown_outcome (no such exception in the database).

Limits: 3 cases is a tiny sample, and the "expected" actions are my own choices. The action list is guidance for a person, not an automatic step.

## Fraud detection: labeled test set (Oct 30)

**All invoices and email texts in this test are SYNTHETIC.** They were generated by
`scripts/make_test_set.py` (fixed random seed) and the labels are in `samples/eval_set.csv`.

**Test set:** 56 invoices, 28 clean and 28 bad. Bad types: changed bank, duplicate copy, no PO,
look-alike vendor, scam email, amount mismatch, no delivery (4 each). Clean types: plain, near the
auto-pay limit, benign email text, and the originals of the duplicates. 10 invoices (one from
each of 10 groups) were set aside as a hold-out and not run or read until the final run.
Run with `python -m scripts.eval` (add `--holdout` once, or `--stub-ai` for code layers only).

### Final numbers

| Run | Frauds caught | Clean wrongly held | Bad wrongly approved | Exact decision |
|---|---|---|---|---|
| Dev split, real Gemini (46) | 21 / 21 | 0 / 25 | **0** | 46 / 46 |
| Hold-out, real Gemini (10, run once) | 7 / 7 | 0 / 3 | **0** | 10 / 10 |
| Dev split, code only, AI replaced by a stub that approves everything (46) | 21 / 21 | 0 / 25 | **0** | 46 / 46 |

Gate (bad invoices wrongly approved = 0): **passed** on all three runs.

### What the failures taught us

- **First code-only run: 19 / 21 caught, 2 bad invoices approved (gate failed).** Two scam emails
  ("settled quietly... don't loop in the usual approvers" and "bank details have changed, effective
  immediately") only scored medium fraud risk because the plain-text scan knew single words, not
  phrases. Fix: the scan now matches phrases (bypassing approval, keeping it quiet, payment demanded
  under pressure, announced bank-detail changes). Single words like "immediately" or "confidential"
  no longer fire, so harmless emails are not flagged.
- **First real-AI run had 2 invoices with `investigator_failed`:** a dropped connection and a DNS
  failure, not rate limits. Fixes: the Gemini call now retries on network errors, and when the AI
  fails the code keeps the hard-check verdict (reject only if a hard check requires it, otherwise
  hold; never approve). The run was repeated and had no AI errors.

### Limits: read these before trusting the numbers

- The data is synthetic and was written by one author (me, with an AI assistant), so the test
  texts share a style. This is a smoke test. It is not evidence of how the system performs on real
  fraud.
- The scam-phrase patterns were changed after seeing two dev misses, so the dev numbers are partly
  fitted. The hold-out is the cleaner number, but it is only 10 invoices (7 bad, 3 clean) with
  one invoice per scenario. A perfect score on 7 frauds cannot rule out a real miss rate well
  above zero.
- The thresholds (2% amount tolerance, 30-day bank-change window, 90% of the auto-pay limit,
  0.8 look-alike similarity) are placeholders chosen by hand, not tuned on real data.
- The hold-out was run once on the same code as the final dev run. Rerunning it after changes would
  turn it into a second dev set.
- Every scam email in the set uses English text. Other languages, scanned PDFs and unusual layouts
  are not covered.
